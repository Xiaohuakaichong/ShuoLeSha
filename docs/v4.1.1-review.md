# 4.1.1 review 与优化记录

日期：2026-10-27。基线是 `feat/v4.1` 分支上**尚未提交**的 4.1 工作区（versionName 4.1，versionCode 28，Room 结构 7），HEAD 为 4.0 的 `c8c2867`。改动前的工作区完整备份在 `_backup/review-2026-10-27/`：`v4.1-uncommitted.patch`、`v4.1-worktree-files.tar.gz`；本次改动单独导出为 `review-changes.diff`。版本升至 4.1.1（versionCode 29）。

## 结论

4.1 的数据安全设计站得住：原稿不可覆盖、显式迁移、数据外发同意、按服务商加密保存密钥，review 中没有发现会丢失原音或原稿的问题。问题集中在三类：

1. 随身录音长时间积累片段后，处理队列和首页的开销按平方增长；
2. 静音或很短的片段可以让一整次记录永远整理不完；
3. 录音服务在“停止后马上开始”时可能进入停不下来的状态。

## 发现与处理

| 级别 | 问题 | 位置 | 处理 |
|---|---|---|---|
| P1 | 静音、零碎应答或很短的片段，模型返回空话题时 `mapTopics` 抛错；MAP 重试 5 次后失败，而 DERIVE 要等所有 MAP 完成，整次记录停在“失败”。提示词要求引用 30–180 字，短片段本身无法满足。 | `AiClient.mapTopics`、`ProcessingCoordinator.isEligible` | 空列表视为有效结果；只有“返回了话题但没有一条能逐字核对”仍算失败。提示词允许短原稿引用整句、允许输出 `{"topics":[]}`。 |
| P1 | `finish()` 把 `finishing` 置真后从不复位。若在 `stopSelf` 前收到新的开始，新录音的停止会直接返回，停止按钮无效；旧的 `stopSelf` 还会结束新录音的前台服务。 | `AudioCaptureService` | `start()` 复位标志；只在主线程确认没有活动录音时才 `stopForeground`/`stopSelf`。 |
| P1 | 每完成一个任务就对全部待处理任务调用一次 `enqueueUniqueWork`。全天随身录音约 288 个片段，离线后补网，加上 MAP 任务，一次排空就是数万次 WorkManager 写入。 | `ProcessingCoordinator.enqueueDurableJobs` | 进程内记录已入队的任务；`UploadWorker` 结束（非 retry）时移除，任务再次待处理时重新入队。 |
| P1 | `onCapabilitiesChanged` 在信号强度、带宽变化时也触发，每次都写库并完整排空队列，移动网络下频繁唤醒。 | `AppContainer` 网络回调 | 只在默认网络获得 INTERNET 或 VALIDATED 时唤醒。 |
| P1 | 生成每日复盘时对当天每个片段重新调用 `mapTopics`，一天 N 个片段就多 N 次模型调用，全程占用串行锁，期间新录音的转写排队。 | `ProcessingCoordinator.digest` | 复用该片段已完成的 MAP 结果（原稿不可变，内容相同），只对没有结果的片段（如旧版文本）调用模型。当天没有可整理话题时不再调用复盘模型。 |
| P1 | 首页卡片在 Compose 中计算，每个会话都扫描全部转写和片段（会话 × 历史转写 × 片段），并为每张话题卡重新解析候选待办的 JSON。录音时每 30 秒检查点、处理中每次状态变化都在主线程重算。 | `MemoryModels.cards()` | 先建索引再遍历，线性复杂度，输出不变。 |
| P1 | 录音页每 200 ms 电平刷新都做一次 转写 × 片段 的扫描。 | `AppNavigation` 录音入口 | `remember` 加集合查找。 |
| P1 | 文档与 4.1 行为不一致：README 写 Room 6、“本地 HTTP 接受私有 IP / `.local`”、密钥按地址隔离；网关说明让手机填 `http://<局域网IP>:8000/v1`，4.1 会把它拦截为“服务地址被拦截”。 | `README.md`、`server/README.md`、`docs/v4-data.md` | 改为结构 7、按服务商保存密钥、外发同意；网关改用 `adb reverse` + `localhost`，无线访问需要受信任证书的 HTTPS。 |
| P2 | 升级前备份只在结构低于 6 时执行，6 升 7 没有副本。 | `AppDatabase.backupBeforeUpgrade` | 每次结构升级前备份到 `files/backups/pre-v<目标结构>/`。 |
| P2 | 备份 ZIP 的 `manifest.json` 结构号写死为 6，实际是 7。 | `BackupMemory` | 使用 `DB_SCHEMA_VERSION`；设置页的结构号也改用常量。 |
| P2 | 详情页订阅全局快照，任何表变化都重读本会话全部原稿，再逐片段读一次完整原稿只为取 `segmentsJson`。 | `DetailViewModel` | 只在本会话相关行变化时重载；时间戳槽位改为一条查询。 |
| P2 | 每个 ViewModel 的 `stateIn` 各自启动一份 8 个 Room 查询，一次表变化按打开的页面数重复执行。 | `MemoryRepository.snapshots` | 仓库层 `shareIn` 共享一份。 |
| P2 | 导入 44.1/48 kHz 音频时直接抽点降到 16 kHz，高频混叠进语音频段。 | `AudioDecoder.decode` | 盒式平均后再取样；16 kHz 的自录音频输出不变。 |
| P2 | 采集循环用“读-复制-写”更新录音状态，可能把已发布的 STOPPING 改回 RECORDING。 | `AudioCaptureService` | 改用 `MutableStateFlow.update`。 |

网关只把健康检查和 OpenAPI 的版本号改为 `4.1.1`，接口行为未变。

## 没有改、建议后续处理

- **串行锁覆盖整个网络请求。** `runOne` 在锁内完成网络调用（单次最长 180 秒，复盘更久）；删除记录、清理原音、导出备份通过 `mutateSession` 等同一把锁，处理进行中这些操作会长时间转圈。建议锁只保护写库，网络调用移出锁外（迟到响应已有校验）。涉及并发语义，应在能跑测试时再改。
- **一个 MAP 永久失败仍会挡住整次记录。** 修复后静音不再触发，但模型连续 5 次返回无法核对的引用时仍会卡住。建议 DERIVE 在所有 MAP 进入终态后用已有结果整理，并标注“部分片段未整理”。
- **启动恢复逐会话查询。** `recover()` 每次启动对每个会话查询片段；记录多了以后“正在打开记忆库”会变长，可改为一条 SQL 找出缺转写的片段。
- **停止时 `stopSelf()` 不带 startId。** 本次已避免误停新录音；改为 `stopSelf(startId)` 更彻底。
- **旧 DAO 方法。** `AudioRecordDao` 中 17 个 v3 时期的方法（如 `markProcessedStructured`、`getOldRecords`、`observeAll`）已无调用，可删除。
- lint 的依赖升级类警告未处理；升级 Room、WorkManager 等之前先看各自更新日志。
